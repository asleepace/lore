# Inbox

Unsorted findings waiting to be triaged into claims or spec changes. Not a node (see `SPEC.md` §9).

## From dogfooding v0 (2026-10-15)

Triaged into v0.1: `verified` dates via blame, markdown markers, tierless decisions, `Rejected:` lines, optional section order and `date`. See `SPEC.md` §13. Still open:

- **[freshness] `covers: [SPEC.md]` is too coarse to be useful.** Any spec edit flags all 5 nodes at low severity, which trains people to ignore it. **Proposal:** allow heading-scoped covers for markdown (`SPEC.md#5-markers`). When a claim has markers, treat covers-only staleness as informational.

- **[format] Root-to-node links break the "ID minus extension" rule** (format#QRK-2). **Options:** (a) accept two link forms and let a formatter fix paths; (b) move the root to `docs/app.md` and keep `APP.md` as a one-line pointer. Leaning (a).

- **[format] The inbox itself has no defined format.** This file improvised one. **Proposal:** bullets of `**[target-node]** finding. **Proposal:** …`, grouped by source.

### Observations for adopters

- **Documenting prose duplicates it.** Here the spec is the "code", so invariants restate its MUST rules. In a code repo invariants aren't duplicated, because code doesn't state them. The value here came from decisions and quirks, which `SPEC.md` doesn't hold.
- **Anchoring is cheap and pays off immediately.** Adding inline markers took a minute and turned every invariant into a checked one.

## From designing Nexus (2026-10-30)

Nexus ([PR](https://github.com/asleepace/nexus/pull/1)) wrote about 120 invariants across 15 docs. A throwaway script that checked every invariant ID resolved found real errors immediately, which is what prompted `lore check` and the [contracts](contracts.md) node.

- **[format] Many short invariants are easier to read as a table.** Nexus docs list 10 to 15 invariants each as `| ID | Invariant | Enforced by |` rows; one `###` heading per claim would triple their length. **Proposal:** allow an optional table form for claim sections (`| INV-n | statement | metadata… |`), with the same IDs and anchors generated by a formatter. Needs a way to keep anchors stable.
- **[freshness] "Enforced by" is a useful field even without markers.** Every Nexus invariant names its mechanism: a type, a database constraint, a test, a health check or review. **Proposal:** an `enforced_by:` claim metadata key; claims whose only enforcement is "review" stay asserted, the rest point at their marker or test.
- **[contracts] Runtime assertions want claim IDs.** See [contracts#DEC-3](contracts.md#dec-3) and [contracts#PLAN-1](contracts.md#plan-1).
- **[format] Nexus docs don't follow Lore v0.1 yet.** They use their own frontmatter (`lore: 1`, `kind`, `type`, `id`) and table-style invariants with `PRO-1`-style IDs. Either Nexus adopts this format for its repo docs, or Lore grows the table form above. Worth deciding before Nexus has code.
