# Lore Spec — v0.2 (draft)

> **L**inked **O**bservations, **R**ationale & **E**dges

This document defines the Lore protocol: the format of the files, the rules tools follow, and how
the format is versioned. It is the only thing a repository needs to adopt Lore; every tool is
optional.

Key words **MUST**, **SHOULD** and **MAY** are used as in RFC 2119.

---

## 1. Principles

1. **Document what code can't say.** Lore holds rationale, invariants, decisions, cross-module behavior, limits and quirks. It MUST NOT restate what is derivable from code (file lists, signatures, call graphs). Derivable content, if wanted, is generated by tools and never hand-edited.
2. **Identity is not position.** IDs never encode where something sits in the graph. Structure lives in metadata and can change freely. <!-- @lore enforces format#INV-1 -->
3. **IDs are links.** Every reference resolves to a plain markdown link with no tooling. <!-- @lore enforces format#INV-3 -->
4. **Progressive enhancement.** Every layer above L0 is opt-in. Deleting all tooling MUST leave the docs valid and useful. <!-- @lore enforces lore#INV-1, layers#INV-1 -->
5. **No tool state in docs.** Frontmatter holds only human-meaningful metadata. Indexes, hashes and caches belong in `.lore/` or git notes. <!-- @lore enforces layers#INV-2 -->
6. **Freshness is a feature.** A reader (usually an agent) must be able to tell how much to trust each claim.
7. **Fit the project, not the other way round.** Projects differ: one app, a monorepo, a docs site. Lore fixes the entry point and the claim format, and leaves where nodes live and what else a node says to the project. <!-- @lore enforces format#DEC-8, format#DEC-9 -->

## 2. Entry point and layout

Every graph starts at **`LORE.md`** in the repository root. It is the root node, it says which
protocol version the graph follows, and it routes to the folders that hold the other nodes.

```
LORE.md                  # root node (id: lore), version and routes
docs/                    # a node folder (the default)
  security.md            # node (id: security)
  moderation.md          # node (id: moderation)
  _inbox.md              # reserved: not a node (see §9)
packages/sdk/lore/       # another node folder, listed in LORE.md
  entities.md            # node (id: entities)
.lore/                   # optional, tool-generated, not hand-edited
```

```markdown
---
lore: 0.2
scope: app
summary: "GameRelay adds multiplayer to single-file browser games."
nodes: [docs, packages/sdk/lore]
---
```

- A repository has exactly one graph and exactly one `LORE.md`, at its root. Its ID is `lore`.
- **`nodes`** lists the node folders, as paths relative to the repository root. Default: `[docs]`.
- Every other node is a `.md` file directly inside a node folder. Each folder MUST stay flat; subdirectories are ignored. <!-- @lore enforces format#DEC-5 -->
- Node IDs MUST be unique across all node folders (lint `L016`).
- Files whose names start with `_` are reserved and are not nodes, in any node folder.
- A folder listed in `nodes` MUST NOT contain markdown files that aren't nodes (other than `_` files). Projects whose `docs/` already holds other documents list a different folder (for example `lore/`) instead.

### 2.1 Routing

`nodes` is the whole routing table: it says where nodes live, nothing else. The zoom tree is still
`parent:` (§6.1), so a node in `packages/sdk/lore/` MAY have a parent in `docs/` and the reverse.
Several folders are for projects where docs belong next to the code they describe (a monorepo's
packages, a published library), not for a second hierarchy. <!-- @lore enforces format#DEC-8 -->

### 2.2 Earlier layouts

- A v0.1 graph has `APP.md` as its root (ID `app`, `spec: lore/0.1`) and MAY name its node folder in `.lore/config.json` (`{ "dir": "lore" }`). Tools MUST read v0.1 graphs (§13): when there is no `LORE.md`, `APP.md` is the root; `app` is accepted as an alias of `lore` in references; `.lore/config.json`'s `dir` acts as `nodes: [dir]`.
- To migrate: rename `APP.md` to `LORE.md`, replace `spec: lore/0.1` with `lore: 0.2`, move any `dir` into `nodes`, and set `parent: lore` where it said `app`. References to `app#…` keep working through the alias; a formatter MAY rewrite them.

## 3. Identifiers

### 3.1 Node IDs

- A node's ID is its filename without `.md`. Frontmatter does not repeat it (a duplicated ID can only drift).
- Charset: `[a-z0-9-]`, starting with a letter. Example: `moderation`, `rate-limits`.
- `LORE.md`'s ID is `lore`; no other node may use it.
- Edge nodes (§6.3) join the two node IDs with `--`: `moderation--llms`.

### 3.2 Claim IDs

```
<TYPE>-<n>
```

| Prefix | Type | Section heading | Meaning |
|---|---|---|---|
| `INV` | Invariant | `## Invariants` | Must always hold. Breaking it is a bug. |
| `DEC` | Decision | `## Decisions` | A choice made, with its rationale and rejected alternatives. |
| `EDGE` | Edge | `## Edges` | Behavior that arises where this node meets another. |
| `LIM` | Limit | `## Limits` | A known constraint or ceiling, accepted on purpose. |
| `QRK` | Quirk | `## Quirks` | Surprising behavior that is intentional or tolerated. |
| `PLAN` | Plan | `## Plans` | Intended future work. Rots fastest. |

- `n` is a positive integer, unique per type within a node.
- Numbers MUST NOT be reused, including after a claim is retired. Gaps are expected. <!-- @lore enforces format#INV-2 -->

### 3.3 References

| Form | Example | Valid in |
|---|---|---|
| Full | `moderation#INV-1` | Anywhere: docs, code markers, commits, PRs |
| Local | `INV-1` | Only inside the node that owns the claim |
| Node | `moderation` | Anywhere a node is meant |

- Matching is case-insensitive. Write IDs uppercase for readability.
- A full reference maps to a link by rule: `node#TYPE-n` → `<folder>/node.md#type-n`, where `<folder>` is the node folder that holds it (`lore#…` → `LORE.md#…`).
- In prose, authors SHOULD write references as links so they work without tooling, with the path relative to the file they're in:
  `[moderation#INV-1](moderation.md#inv-1)` between nodes in one folder, `[moderation#INV-1](docs/moderation.md#inv-1)` from `LORE.md`. Tools MUST also recognize bare references, and a formatter MAY fix paths.

## 4. Node format

```markdown
---
scope: feature
parent: security
summary: "Pre-publish content screening: an LLM classifier with a rules fallback."
covers: [src/moderation/**, src/api/posts/create.ts]
links:
  - { to: llms, rel: depends_on, note: "classifier model choice, see DEC-3" }
verified: 2026-10-15
---

# Moderation

Optional free-form context. Keep it short; claims carry the weight.

## Invariants

### INV-1
No post is visible to other users before a moderation verdict exists.

The create endpoint writes posts as `pending`; only the verdict worker flips them.
Readers filter on `status = 'visible'`, never on `!= 'hidden'`.

- tests: tests/moderation/visibility.test.ts

## Decisions

### DEC-3
Use a small hosted classifier instead of a frontier model for first-pass screening.

The p95 latency budget for post creation is 200ms. Frontier models measured 800ms+.
Rejected: async-only moderation (would violate INV-1 or block the UI).

## Notes

Anything that matters but isn't a claim: a glossary, a diagram, open questions, how to run
the thing locally.
```

### 4.1 Frontmatter

Frontmatter is YAML. **Quote `summary`** (and any other prose value): a sentence with a colon in it
is not valid YAML unquoted, and a node whose frontmatter doesn't parse is invalid (`L015`).

| Field | Required | Description |
|---|---|---|
| `lore` | `LORE.md` only | Protocol version, `<major>.<minor>` (§12). |
| `nodes` | no, `LORE.md` only | Node folders (§2). Default `[docs]`. |
| `scope` | yes | `app` \| `domain` \| `feature` \| `edge` |
| `parent` | yes, except `LORE.md` | Node ID of the parent. Forms the zoom tree. |
| `summary` | yes | One sentence. Lets a reader decide whether to open the node. |
| `covers` | no | Globs of files this node describes. Drives node-level staleness. Keep it narrow (§8). |
| `links` | no | Typed outbound links: `{ to, rel, note? }`. |
| `verified` | no | Date (`2026-10-15`) a human or agent last confirmed the node is accurate. See §4.1.1. |
| `review_after` | conditional | Date (`2027-01-15`) or duration (`90d`) after `verified`. Required when the node has no `covers` and no markers point at it. |
| `status` | no | `active` (default) \| `deprecated` |

Projects MAY add their own fields (`owner: payments-team`). Tools MUST ignore fields they don't know (§12.2). <!-- @lore enforces layers#INV-3 -->

#### 4.1.1 Verification commit

The **verification commit** of a node is the commit that last changed its `verified:` line. Tools MUST derive it with `git blame` rather than read a SHA from the file. <!-- @lore enforces freshness#DEC-3 -->

This lets an edit and its verification land in the same commit: a commit cannot contain its own SHA, but blame can point at it afterwards. Without git history (e.g. a tarball), tools fall back to comparing the `verified` date against file modification dates.

Link `rel` values: `depends_on`, `interacts_with`, `related`. Tools MUST accept unknown values and treat them as `related`.

### 4.2 Body

1. One `# Title` (H1).
2. **Claim sections**: `## Invariants`, `## Decisions`, `## Edges`, `## Limits`, `## Quirks`, `## Plans`. Each optional. They SHOULD appear in this order, but order carries no meaning, so formatters MAY reorder them and lint MUST NOT treat order as an error. <!-- @lore enforces format#DEC-7 -->
3. **Open sections**: any other `##` heading (`## Context`, `## Notes`, `## Glossary`, `## Open questions`, `## Comments`, or anything else). As many as needed, anywhere in the node, before, between or after claim sections. An open section holds anything that matters but isn't a claim, in any markdown. It MUST NOT contain claims (an `### INV-1` heading there is `L003`). <!-- @lore enforces format#DEC-9 -->

Tools MUST NOT parse open sections for meaning: they are for readers. Staleness still covers them at node level, through `covers` and `verified`.

### 4.3 Claims

- A claim is an `###` heading containing **only** its local ID: `### INV-1`. No title text, so the anchor (`#inv-1`) never changes when wording does.
- The claim's prefix MUST match its section.
- **The first paragraph is the claim.** It SHOULD be one sentence of ≤ 30 words. Everything after it is rationale and context.
- **A `DEC` claim SHOULD include a line starting with `Rejected:`** naming the alternatives that were considered and why each lost. This is often the most useful line for an agent, because it stops ideas that were already ruled out from being proposed again. <!-- @lore enforces format#DEC-6 --> `Rejected:` starts its own line; a formatter MAY move one written mid-paragraph.
- A claim MAY end with a metadata list. Each item is `- key: value`. Recognized keys:

| Key | Meaning |
|---|---|
| `status` | `active` (default) \| `superseded` \| `retired` |
| `superseded_by` | Reference to the replacing claim. Implies `status: superseded`. |
| `date` | Optional. Only for a claim recorded after the fact (`YYYY-MM` or `YYYY-MM-DD`); otherwise git history already dates it. |
| `review_after` | Date or duration. Required for `PLAN`. |
| `tests` | Comma-separated paths to tests that enforce this claim. |

  Tools MUST ignore metadata keys they don't know.
- Claims are never deleted. To retire one, set `status` and leave the heading in place as a tombstone.

### 4.4 Comments

A comment is a remark about a claim or a node that isn't part of it: a question, a doubt, a
reviewer's note, a "this bit us again on 2026-11-02". Comments are optional and come in two forms: <!-- @lore enforces format#DEC-10 -->

- **On a claim:** a blockquote after the claim's text (before or after its metadata), starting with who and when:

  ```markdown
  ### LIM-2
  At most 4 bots a room.

  > **colin, 2026-10-16:** racecar wants 7 AI drivers; revisit with bot seats.
  ```

- **On the node:** a `## Comments` open section (§4.2), same convention.

Comments are not claims: they have no IDs, no tier and no staleness of their own, and lint ignores
them. An L4 agent MAY add a comment (signed `agent, <date>`) but MUST NOT edit or remove anyone
else's. A comment that turns out to be true belongs in a claim; one that's settled can be deleted
in a normal edit.

HTML comments (`<!-- … -->`) are also allowed anywhere and ignored, except markers (§5.1).

### 4.5 Size

Nodes SHOULD stay under 300 lines. A node that outgrows that SHOULD split into child nodes (`parent:` pointing back).

## 5. Markers (code → claims)

Any comment in any language MAY contain a marker:

```
@lore <verb> <ref>[, <ref>...]
```

```ts
// @lore enforces moderation#INV-1
if (post.status !== 'visible') return notFound()
```

```py
# @lore implements moderation#DEC-3, llms#DEC-2
```

| Verb | Meaning | Staleness weight |
|---|---|---|
| `enforces` | This code is what makes the claim true. | high |
| `implements` | This code carries out the claim. | medium |
| `see` | Related; read the claim for context. | none |

- Markers MUST use full references. <!-- @lore enforces markers#INV-1 -->
- **Placement:** a marker MAY sit on the line above the code it anchors, or at the end of the first line it anchors.
- **Region (v0 heuristic):** a marker anchors from its own line to the next blank line or the next marker, capped at 50 lines. Language-aware adapters (e.g. tree-sitter) MAY narrow this to the enclosing symbol.

### 5.1 Markers in markdown

Markdown files (specs, READMEs, runbooks) can anchor claims too. In a markdown file, a marker MUST be inside an HTML comment, which renders invisibly:

```markdown
1. Retries are capped at three. <!-- @lore enforces jobs#INV-2 -->
```

Tools MUST ignore markers inside fenced code blocks and inline code spans in markdown. Those are examples, not anchors. <!-- @lore enforces markers#DEC-3 -->

## 6. Graph

### 6.1 Tree

`parent` links form a tree rooted at `lore`. It is the zoom axis: higher is broader, deeper is more specific. The tree MUST be acyclic and every node MUST reach `lore`, whichever folder it lives in.

### 6.2 Graph

`links`, references in prose and markers form the wider graph. They MAY cross the tree, and node folders, in any direction.

### 6.3 Edges

Behavior where two nodes meet is recorded as an `EDGE` claim in the node on the **consuming** side, linking to the other node. When an interaction grows beyond a few claims, it MAY be promoted to its own node with `scope: edge` and an ID of `a--b` (alphabetical order).

## 7. Trust

Every active `INV`, `EDGE`, `LIM` and `QRK` claim has a trust tier, highest first:

| Tier | Condition |
|---|---|
| **tested** | Has a `tests:` entry, or an `enforces` marker inside a test file. |
| **anchored** | At least one `enforces` or `implements` marker points at it. |
| **asserted** | Prose only. |

`DEC` and `PLAN` claims have no tier. They record history and intent, which nothing can enforce, so tools MUST NOT count them as asserted. <!-- @lore enforces freshness#DEC-4 -->

A claim's **freshness** is separate from its tier: a claim is **stale** when its anchors changed after the node's verification commit (§4.1.1, §8), or when `review_after` has passed.

Readers (including agents) SHOULD weight claims by tier and freshness. Tools SHOULD surface both.

## 8. Staleness

Given a diff (a PR or a commit range), a claim is **affected** when:

| Signal | Severity |
|---|---|
| A changed hunk intersects an `enforces` marker region | high |
| A changed hunk intersects an `implements` marker region | medium |
| A marker referencing the claim was removed | high (orphaned anchor) |
| A file matching the node's `covers` changed | low (whole node) |
| A file in `tests:` changed or was deleted | medium |

`see` markers never affect a claim. Detection MUST be deterministic and MUST NOT require an LLM. <!-- @lore enforces freshness#INV-1 -->

`covers` SHOULD name the files a node is about, not files every change touches. A large shared file
(a server's main module, a spec) in `covers` flags the node on most commits and teaches people to
ignore it; anchor the relevant region with markers instead.

## 9. Capture (optional)

- **Commit trailers.** Commits MAY carry `Lore-Claim: moderation#DEC-4` (a new or changed claim) or `Lore-Impact: moderation` (a node likely needs updating).
- **Inbox.** `_inbox.md` in any node folder MAY collect unsorted findings from agent sessions or reviews. It is triaged into real claims and is not a node. Suggested shape: bullets of `**[target-node]** finding. **Proposal:** …`, grouped by source under `##` headings.

## 10. Lint rules

| Code | Level | Rule |
|---|---|---|
| `L001` | error | Reference to a nonexistent node or claim |
| `L002` | error | Duplicate claim ID within a node |
| `L003` | error | Claim prefix does not match its section, or a claim inside an open section |
| `L004` | error | Missing required frontmatter field |
| `L005` | error | `parent` missing, cyclic, or not reaching `lore` |
| `L006` | error | Marker uses a local reference or unknown verb |
| `L007` | warn | `PLAN` claim without `review_after` |
| `L008` | warn | `review_after` has passed |
| `L009` | warn | Unanchored node without `review_after` |
| `L010` | warn | Node over 300 lines |
| `L011` | warn | Claim's first paragraph over 30 words |
| `L012` | warn | Claim heading contains text besides the ID |
| `L013` | info | `DEC` claim without a `Rejected:` line |
| `L014` | info | Claim sections out of the recommended order (fixable by a formatter) |
| `L015` | error | Frontmatter is not valid YAML |
| `L016` | error | Two node folders hold the same node ID |
| `L017` | error | A node folder holds a markdown file that isn't a node (no frontmatter) |
| `L018` | error | `lore` version missing, or a major version the tool doesn't support |

Tools MUST NOT report open sections, unknown frontmatter fields, unknown metadata keys or comments.

## 11. Conformance levels

| Level | Adds | Requires |
|---|---|---|
| **L0** Format | This spec, §2–§4, §6 | Nothing |
| **L1** Markers | §5 | Nothing (grep) |
| **L2** CLI | §7, §8, §10 locally | `lore` binary |
| **L3** CI | §8 on every PR | GitHub Action |
| **L4** Agent | Proposed updates to affected claims, inbox triage | Model API key |
| **L5** Push | Inject relevant claims when an agent opens a covered file | Claude Code hook / MCP |

An L4 agent MUST only edit affected nodes, MUST NOT delete claims, MUST NOT edit generated content and MUST NOT edit others' comments (§4.4). Its changes go through normal PR review.

## 12. Versioning

Lore is a protocol, versioned so that a repository, a tool and an agent can tell whether they
agree. <!-- @lore enforces layers#DEC-3 -->

### 12.1 The version

- `LORE.md` declares the version its graph follows: `lore: <major>.<minor>` (for example `lore: 0.2`). It is required (`L018`).
- This document is the specification of the version in its title. Each version is tagged in this repository as `v<major>.<minor>` and listed in §14.

### 12.2 Compatibility

- **From 1.0:** a **minor** version only adds: new optional frontmatter fields, metadata keys, sections, lint rules at `warn` or `info`, conformance levels. Every graph valid under `1.n` is valid under `1.n+1`. A **major** version may change or remove anything, and ships with migration notes.
- **Before 1.0:** any minor version may break, and ships with migration notes (§2.2 is the first).
- Tools MUST ignore what they don't know: frontmatter fields, metadata keys, `##` sections, `rel` values. That is what makes minor versions safe. <!-- @lore enforces layers#INV-3 -->
- A tool MUST read every minor version of the majors it supports, and MUST report `L018` instead of guessing on a newer major.
- An L4 agent MUST NOT change `lore:`; upgrading the protocol is a human decision.

## 13. Open questions

- Should `verified` live per claim (more precise) or per node (less noise)? v0.2 says node.
- Is the 50-line marker region heuristic good enough before tree-sitter?
- Should `covers` be allowed on claims, not just nodes? Should it accept heading anchors in markdown (`SPEC.md#5-markers`) so a shared file doesn't flag every node?
- How should a node be renamed? (Every reference to it breaks. Candidate: a `moved_to:` tombstone node.)
- **Should `LIM` be tierless, like `DEC`?** In the GameRelay trial, most "asserted" claims were accepted limits ("one relay host") or invariants about absence ("no runtime dependencies"), and some are enforced by JSON files that can't hold a marker. Candidates: tierless `LIM`; a `files:` metadata key that backs a claim with files that can't carry markers.
- **Markers in published code.** Code mirrored to a public repository (a library's package) carries markers pointing into a graph its readers can't open. Candidates: an export step that strips markers; a node folder that ships with the package (§2), so the package's own claims travel with it.
- **Comments in practice:** is a signed blockquote (§4.4) enough, or do comments need IDs so they can be resolved and referenced?

## 14. Changelog

### v0.2 (2026-10-16, draft)

From the GameRelay trial (a 10-node, 68-claim graph on its monorepo; asleepace/gamerelay.io#225) and the founder's direction:

- **`LORE.md` is the entry point and root node** (ID `lore`), replacing `APP.md` (ID `app`). It carries the protocol version and routes to node folders (§2).
- **Several node folders** through `nodes:` in `LORE.md`, replacing `.lore/config.json`'s `dir`. Node IDs stay unique across folders (`L016`); folders stay flat; the tree is still `parent:` (§2.1).
- **Versioning** (§12): `lore: <major>.<minor>` in `LORE.md` (was `spec: lore/0.1`), compatibility rules, tools ignore what they don't know, migration notes for v0.1 (§2.2).
- **Open sections** (§4.2): any non-claim `##` section, as many as needed, anywhere in a node. Was: optional free-form sections before the claims only.
- **Comments** (§4.4): signed blockquotes on a claim, or a `## Comments` section; ignored by lint; agents may add but never edit others'.
- **Quote `summary`** (§4.1): 6 of 11 summaries in the trial were invalid YAML unquoted. New `L015`.
- **Projects may add their own frontmatter fields**; tools ignore unknown fields and metadata keys.
- **`covers` guidance** (§8): keep it narrow. In the trial, one shared 1,700-line file in `covers` would have flagged its node on 18 of the last 80 commits.
- **`Rejected:` starts its own line** (§4.3). 7 of 26 trial decisions wrote it mid-paragraph.
- New lint rules `L015`–`L018`; `L003` also covers claims inside open sections.
- Inbox shape suggested (§9); `_inbox.md` allowed in any node folder.

### v0.1 (2026-10-15)

From dogfooding v0 on this repository:

- `verified_at: <sha>` → `verified: <date>`; the verification commit comes from `git blame` (§4.1.1). Fixes nodes being born stale.
- Markers in markdown are defined: HTML comments only; fenced code and inline code are ignored (§5.1). Markers may sit at the end of a line (§5).
- Trust tiers exclude `DEC` and `PLAN` claims (§7).
- `Rejected:` line recommended for decisions (§4.3); new info rule `L013`.
- Section order is a recommendation, not an error (§4.2); new info rule `L014`.
- `date` metadata is optional and only for claims recorded after the fact (§4.3).
